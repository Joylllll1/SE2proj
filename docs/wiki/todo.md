## 实时推送升级（SSE 替代轮询）

**背景**：首页当前使用 60s 轮询检查新帖子，最长有 60s 延迟。

**建议方案**：SSE (Server-Sent Events)

| 方案 | 成本 | 延迟 | 适用场景 |
|------|------|------|----------|
| **SSE** | 无需新依赖，原生支持 | 即时 | 单向推送，完全满足需求 |
| WebSocket | 需 socket.io 前后端改动 | 即时 | 双向通信，需求过剩 |

### 实现要点

**后端**：
- Express 路由 `GET /api/events`
- PostService/createPost 完成后通知 SSE 客户端
- 客户端断连自动清理

**前端**：
- `HomePage.jsx` 中用 `new EventSource('/api/events')` 替换轮询 `setInterval`
- 收到事件后调 `fetchPosts()` 增量更新

### 优先级

低 — 当前 60s 轮询对校园匿名社区可接受。建议排在以下功能之后：
- [ ] 我的喜爱页面
- [ ] 后台管理功能
- [ ] 博主回复管理

## 点赞通知语义优化

**背景**：当前通知中心会把同一帖子上的多条点赞通知合并显示。最低成本修复已改成“收到新的点赞”，避免把重复点赞事件错误表述成“3 人点赞”。

**后续优化目标**：让通知既能合并展示，又能正确表达“唯一点赞用户数”。

### 最低成本方案

- 保持现有通知模型不变
- 前端继续按帖子聚合同类点赞通知
- 文案只写“你的帖子收到了新的点赞”，不显示人数

### 推荐优化方案

- 在点赞通知中记录 `actorUserId`，表示是谁触发了这次点赞
- 后端为“同一用户 + 同一帖子 + 未读点赞通知”做去重或 upsert
- 用户取消点赞后，可选择删除对应未读通知或将其标记失效
- 前端聚合时按唯一 `actorUserId` 统计人数，再决定是否显示“3 人赞了你”

### 进一步可选项

- 若未来想做“谁赞了我”，可额外记录触发者昵称快照或匿名展示名快照
- 若未来想减少通知噪音，可只保留最新一条未读点赞聚合通知

## 页面搜索能力补全

**背景**：顶部搜索框当前是全局输入框，但很多页面只显示输入，没有真正消费搜索条件，用户会以为“能搜但没反应”。

### 已采用的最低成本方案

- 将搜索定义为“页面内搜索”，不是全站统一搜索
- 首页、收藏页、我的喜爱页、校园公告页各自消费同一份 `uiStore.query`
- 前端用统一匹配函数过滤当前页面已加载的数据，先把体验接通

### 后续优化方向

- 把搜索词写入 URL，例如 `?q=...`，保证刷新、回退、分享后状态一致
- 根据页面动态调整搜索框 placeholder，明确“当前在搜什么”
- 数据量变大后，把收藏、点赞、活动搜索下沉到后端接口
- 进一步统一 selector / matcher，减少页面级过滤逻辑分散

## 登录态失效处理优化

**背景**：当前 access token 默认 15 分钟过期，refresh token 默认 7 天有效。应用启动时会尝试 refresh，但用户正在使用时如果接口返回 401，前端会直接清空本地 token 并跳回首页，体验比较生硬。

### 当前问题

- 会话恢复和运行时请求的 token 失效处理不一致
- 运行时命中 401 时，没有先尝试 refresh，而是直接掉登录
- 用户可能在编辑、浏览或交互中被突然踢回未登录态
- `logout` 目前只清本地 token，没有服务端 refresh token 吊销机制

### 最低成本方案

- 在前端通用请求层统一处理 401
- 若 access token 失效且本地有 refresh token，先调用 `/api/auth/refresh`
- refresh 成功后重放原请求，用户无感继续使用
- refresh 失败时再清空本地登录态并跳转登录页

### 推荐优化方案

- 在 `apiClient` 中做单飞 refresh，避免多个并发 401 同时刷新
- 区分 `TOKEN_EXPIRED`、`INVALID_TOKEN`、`USER_NOT_FOUND`，只对可恢复场景尝试 refresh
- 对“正在编辑”类页面补一个登录失效提示，避免用户误以为内容丢失
- 未登录后的默认落点从首页改成登录页或带提示的会话过期页

### 进一步可选项

- 后端为 refresh token 增加版本号、黑名单或持久化存储，支持主动失效
- `logout` 时同步吊销 refresh token，减少旧 token 在有效期内继续可刷新的风险
- 若未来需要更细控制，可按设备维度管理会话
